## What this is

A Django web app for managing shared household chores: a status board, history log, and ownership map, visible to every household member. See [_docs/_plan.md](_docs/_plan.md) for the full product scope and [_docs/backlog.md](_docs/backlog.md) for the task breakdown the codebase was built against.

## Commands

Dependencies and the virtualenv are managed with `uv` (`.venv/`, `pyproject.toml`, `uv.lock`) — always run Django through it, not a bare `python`.

```
uv sync                                          # install dependencies
uv run python manage.py runserver                # dev server at 127.0.0.1:8000
uv run python manage.py makemigrations chores_app
uv run python manage.py migrate
uv run python manage.py test chores_app          # full test suite
uv run python manage.py test chores_app.tests.test_conflict                      # one file
uv run python manage.py test chores_app.tests.test_conflict.EscalatedBoundaryTests.test_due_4_days_ago_is_escalated  # one test
uv run python manage.py seed_demo_data           # wipes and reseeds demo data (see README)
uv add <package>                                 # add a dependency
```

No linter is configured in this project.

## Architecture

**Project vs. app**: `chores_config/` is the Django project (settings, root urls, wsgi/asgi). `chores_app/` is the one Django app containing all feature code. The app's URL namespace is intentionally still `chores` (`app_name = 'chores'` in `chores_app/urls.py`, used as `{% url 'chores:status_board' %}` etc.) even though the package was renamed from `chores` to `chores_app` — it's a URL label, not a Python import path, and templates depend on it.

**Single household assumption**: `Household` exists as a model, but `Chore` has no FK to it — the app assumes one household per deployment. Don't add multi-tenancy scoping without checking whether that assumption still holds.

**Chore/ChoreInstance split**: `Chore` is the recurring template (name, priority, recurrence rule, assignment rule). `ChoreInstance` is one dated occurrence of it (due date, status, who's assigned/completed it). Recurrence fields (`recurrence_type` + `interval_days`/`weekdays`) live directly on `Chore` rather than a separate `RecurrenceRule` model — this was a deliberate simplicity choice, not an oversight.

**Instance generation and assignment are coupled**: `Chore.create_next_instance()` computes the due date via `next_due_date()` *and* resolves the assignee via `_next_assignee()` in the same call, dispatching on `assignment_type`:
- `fixed` → `fixed_assignee`
- `rotating` → `_advance_rotation()`, which indexes into `rotation_members` ordered by `id` and advances/persists `rotation_next_index` (an index, not a popped queue, so membership can change between turns without losing position)
- `pool` → left unassigned (`None`), for self-claim via `ChoreInstance.claim(user)`

Deadline-based chores (`recurrence_type='deadline'`) don't generate on a schedule — `ChoreInstance.mark_done()` calls `create_next_instance()` on completion only for that recurrence type. Interval/weekday chores are expected to be generated by some external schedule (no cron/management command for this exists yet).

**Flagging is computed, not stored**: `ChoreInstance.is_overdue`/`is_unclaimed` are properties computed from `status`/`due_date`/`assigned_to` at read time. `ChoreInstance.STATUS_OVERDUE` exists as a status choice but is never actually set by any code path — overdue-ness is always derived, not transitioned into. Query-level equivalents (`.overdue()`, `.unclaimed()`, `.flagged()`, `.escalated(days=3)`) live on `ChoreInstanceQuerySet`, bound as `ChoreInstance.objects` via `Manager.from_queryset(...)`.

**Two separate admin concepts**: Django's own `is_staff`/`is_superuser` control login to `/admin/` at all. `Profile.is_admin` is a separate, app-level "household admin" flag. `chores_app/admin.py` gates add/change/delete on `Chore`/`ChoreInstance` specifically behind `Profile.is_admin` (via `AdminOnlyModelAdmin`, checking `request.user.profile.is_admin` and treating a missing `Profile` as non-admin). `Household`/`Profile` stay registered with Django's plain defaults — they're dev-inspection tools, not part of the permission model. There is no custom create/edit view for chores; Django admin is the only place chores are authored.

**Views are function-based**, all `@login_required`, in `chores_app/views.py`: `status_board`, `history`, `ownership_map` (GET) and `claim_instance`, `mark_done` (`@require_POST`, catch `ValueError`/redirect rather than 500 on invalid actions like double-claiming). No role-based view restrictions beyond login — per the plan, all members see the same data.

**Notifications are a live query, not a model**: `chores_app/context_processors.py` injects `flagged_count` (`ChoreInstance.objects.flagged().count()`) into every template's context — registered in `chores_config/settings.py`'s `TEMPLATES[...]['OPTIONS']['context_processors']`. There's no persisted Notification/read-state model by design.

**Tests** live under `chores_app/tests/` as a package (one file per feature area — foundation models, core models, assignment, completion, conflict/flagging, views, admin permissions, seed command), not a single `tests.py`.

**`seed_demo_data`** (`chores_app/management/commands/seed_demo_data.py`) is idempotent-ish: if its demo household already exists, it deletes it (cascading through chores/instances/profiles/users) and reseeds fresh rather than accumulating duplicates.
